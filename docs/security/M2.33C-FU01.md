# M2.33C-FU01: authorization revocation during chat delivery

The simple broker's subscription registry matches destinations against subscriptions
created earlier. It does not revisit account status or room membership when it
fans out a server broadcast. Outbound room MESSAGE headers identify the recipient
session and subscription; any principal copied from the original message must not
be treated as the recipient's identity.

## Reproduction

Before the fix, four broker regressions failed (4 failures, 0 errors, 0 skipped):
TEXT and IMAGE delivery after account deactivation, and TEXT and IMAGE delivery
after membership removal. Each test first confirmed both synthetic members could
receive a broadcast, revoked one member, then observed that both still received
the next broadcast. No database or network server was used.

## Delivery policy

`ChatOutboundAuthorization` implements Spring's `ExecutorChannelInterceptor` and
runs on `clientOutboundChannel` in `beforeHandle`. This hook runs after executor
queuing, immediately before each outbound handler. A check only in `preSend`
would miss revocation while a message waited in the executor queue.

The transport decorator attached to the existing SockJS/WebSocket endpoint tracks
open transports and supplies each recipient's existing session principal. No new
credentials or authentication mechanism are introduced. Each protected MESSAGE
must target an exact positive-Long room destination, have a known open transport,
resolve to an existing ACTIVE user through `CurrentUserService`, and pass the
current `ChatService.isMember` check. Unknown identities, malformed destinations,
deleted accounts and lookup failures silently drop that recipient's delivery.
Protocol control messages and cleanup frames pass normally. No private payload
or lookup exception is logged by the guard, and a denial does not throw into the
broker's payload-bearing error logging path or affect another recipient.

There is no cached authorization decision and no custom subscription registry.
Spring continues removing subscriptions on UNSUBSCRIBE and DISCONNECT. A revoked
subscription can remain registered but cannot deliver while permission is absent;
if permission is restored, the next delivery is checked again and may succeed.

## Lifecycle and cost

The only additional state is one transport reference per open WebSocket/SockJS
session, regardless of its message or subscription count. Close callbacks,
transport errors, failed connection establishment, and bean destruction remove
state. Identity-conditional removal prevents a late callback from removing a
replacement transport. No message bodies, per-user permission caches, history,
or per-subscription entries are retained.

An attempted delivery to an active recipient uses one user lookup and one room
membership lookup, on the outbound executor. Inactive/missing accounts stop after
the user lookup; unknown transports and malformed destinations query neither.
Multiple connections and subscriptions are checked independently. With the
production transport handler this means up to two repository calls per recipient
MESSAGE, in addition to existing inbound checks. Additional outbound consumers
also receive independent checks. This deliberately avoids permission-cache
revocation delays. Database load and outbound executor latency should be measured
before high-volume deployment; no live database benchmark was performed.

## Limits

The HTTP logout/session-expiration integration that remained after FU01 is now
implemented by FU02. See [M2.33C-FU02](M2.33C-FU02.md) for the servlet session
binding, revocation, final-write guard and lifecycle validation. FU01 account
status and room membership checks remain in place.

A completed check cannot retract bytes already handed to the transport, and a
concurrent database change after the check is not atomic with a network write.
The guard reads current repository state immediately before handling and rechecks
each subsequent delivery, including messages waiting in the outbound executor.

Tests use the actual configured Spring broker, endpoint decorator, message handler,
mocked repositories and synthetic transports. A controllable outbound executor
verifies revocation after enqueueing. Tests also assert the revoked transport's
`sendMessage` is never called, while the authorized transport still receives the
broadcast. Lifecycle, error, malformed-header and query-count tests supplement the
broker tests. No live accounts, MySQL, real media or browser sessions are used.


Final validation: 240 Java tests passed (76 inbound, 13 broker, 31 outbound,
and the existing 120 security regression tests). All 41 Node security tests
passed. Both runs had zero failures, errors and skipped tests. Java test
instrumentation required an approved Maven run outside the sandbox. JavaScript
syntax checks also passed. Browser/network handshake verification was not run.
