# M2.33C-FU02: servlet-session revocation for chat

## Architecture and reproduction

The application uses servlet HTTP sessions and Spring Security's session security
context. Local login writes an OAuth2-shaped Authentication into that context;
OAuth2 login also uses the existing session security context. Spring Session is
neither declared nor present in the dependency tree. Both frontend logout flows
POST to `/logout` using CSRF protection. The existing SecurityConfig invalidates
the HTTP session and deletes its cookies; that policy is unchanged.

FU01 retained a transport principal, which remains usable after servlet-session
invalidation. The first ten isolated broker regressions failed before FU02:
six TEXT/IMAGE cases covering logout, explicit invalidation and real Tomcat idle
expiry, and four SEND/SUBSCRIBE cases after logout/invalidation. Delivery tests
used two sockets belonging to the revoked session and another valid HTTP session
for the same synthetic user. No real accounts, database or network server were used.

## Binding and enforcement

The configured handshake interceptor retrieves `getSession(false)` from the
trusted servlet request. It copies an opaque `ChatHttpSessionBinding` into the
server's transport attributes, after checking the request principal against the
session security context. Client headers, cookies containing guessed IDs and
STOMP native headers cannot construct that capability. This interceptor applies
to both existing SockJS transports and the existing `/ws/websocket` raw route.

A binding is an `HttpSessionBindingListener` attribute of its originating HTTP
session. Servlet invalidation and container expiration unbind it automatically;
no extra listener registration, Spring Session, scheduler or external service is
needed. The callback publishes a volatile revoked flag and clears its connection
registry before attempting transport closes. Registry locks are released before
I/O. Failed/interrupted closes do not restore access or prevent attempts to close
other connections. The outbound transport registry is detached even if the close
fails or its callback never arrives. Normal close/error callbacks and shutdown
also unregister connections; repeated cleanup is safe.

Inbound CONNECT/STOMP, SEND and SUBSCRIBE require a live binding as well as the
existing account/membership checks. Binding checks run again after repository
lookups and on the inbound executor, blocking operations queued before logout.
DISCONNECT, UNSUBSCRIBE and heartbeat cleanup remain available.

Outbound room delivery checks the binding before and after FU01 authorization.
A session decorator inside Spring's transport write buffer checks it again at the
final `sendMessage` call, also requiring the transport registration to remain
current. Thus a message that passed outbound authorization before logout cannot
bypass revocation by waiting for a later transport write. Denials return without
logging private content, credentials, cookies or session IDs.

## Session isolation, cost and limits

All sockets sharing one HTTP session share its binding. Logout/invalidation closes
and revokes those sockets, while another valid session for the same user remains
authorized. Session-ID rotation preserves the association because it is based on
the server object, not an ID string. An old revoked capability cannot be revived;
a fresh authenticated HTTP session and handshake create a new valid association.
The existing local login endpoint and OAuth2-shaped sessions are exercised in tests.

State is one binding per HTTP session that has attempted chat, plus entries for
open transports. No global session-ID/tombstone registry, message history or
permission cache is introduced. Normal disconnect/error cleanup removes transport
entries; unbinding clears all of the affected session's entries. The new checks
read session state in memory and add no database calls. FU01 still performs up to
two repository lookups per active recipient delivery.

The servlet container remains authoritative for idle expiration and dispatches
the unbinding callback when it expires a session. These checks do not refresh its
last-access time. Actual SockJS HTTP requests can refresh it through ordinary
servlet request processing. There is no separate chat inactivity timer.

Bytes already admitted to a network write before revocation cannot be recalled;
the final gate rejects later write attempts once revocation is observed. Operations
already executing before revocation are not transactionally rolled back; queued
protected operations are denied. No database transaction is atomic with a network
write. Close failures may leave an underlying socket physically open until its
transport/container cleans it up, but its private delivery and protected inbound
operations remain denied. This implementation targets the current single-process
servlet-session architecture; distributed session replacement would need its own
lifecycle integration.

## Validation

Before fix: 10 failures, 0 errors, 0 skipped. After fix: 270 Java tests and 41 Node
tests passed, with 0 failures, errors or skips. Java totals: 76 inbound, 25 broker,
31 outbound, 18 new lifecycle tests and 120 existing upload/media/password security
regressions. Additional cases cover queued inbound/outbound work, final writes,
concurrent invalidation/registration, slow/failed/interrupted closes, repeated
cleanup, session-ID rotation, valid local re-login, independent sessions and actual
SockJS/raw-route dispatch. Tests use real Spring logout filtering and real Tomcat
session expiration/unbinding objects, synthetic transports and mocked repositories.
No live browser, network handshake, external OAuth provider or live-container
expiration scheduler was exercised. The container's expiration method and listener
callbacks were exercised directly, without starting a server.
